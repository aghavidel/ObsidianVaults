# Correct Measurement and Benchmarking

The lecture today is a little bit different. It is a meta-review of how we measure things in distributed systems, and what those numbers means.

For our intents and concerns, we want to main measurements of any system (which means we also need multiple other measurements that require the previous ones to be accurate).
- Latency: Overall time between a request and a response
	- Part of this is dictated by network
	- Part of this is dictated by processing at destination

- Throughput (Goodput): The number of (valid) requests per unit time
	- One problem with measuring this is that the system can have queues within it forming.
	- These queues will prevent us from seeing the maximum throughput of a system

Throughput often can be measure in conjunction with latency. The throughput is determined by the component with the largest delay. That component ends up becoming the bottleneck.
- Knowing what the bottleneck is, it is not only useful for checking your system, it is also important in terms of design.
- Load generation needs to be done carefully. 
  If we send too many requests, we will create queues, and we will drop the throughput.
  There are two ways of doing this:
	- *Closed Loop Measurement:* Have a pool of clients that issue a very small amount of requests. Increase the number of clients to increase the level.
	  This tends to be more gentle and prevent some queuing delays, since clients tend to be synchronous and will not issue new requests if their previous ones are not done.
	- *Open Loop Measurement:* Load is generated independently, usually according to some distribution (think of it like picking flows from some distribution). 
	  This is nice for exerting more control on how requests are generated.

When measuring maximum throughput with a closed-loop scenario, you must increase the number of clients from very few, up until you see the throughput stop climbing. At that point you would see that the latency is climbing very fast. For this reason, a *throughput-latency* graph tends to be quite useful.

The key-insight here is that you probably don't want to operate at maximum throughput for prolonged periods of time. The reason for this is that operating at maximum load will create queues, and these queues will heavily increase the latency.
To have maximum throughputs, you need to have queues that are almost standing, meaning that they never seem to deplete, but never overflow as well.

The problem is that operating at this knife-edge means that you are not resilient to *load bursts*, which are very common. So if a series of clients suddenly issue a huge number of requests, they will increase the queue length dramatically, which means that your system not only experiences high latency, it will also probably drop requests at some point.

So you want to keep-away from fully utilizing the system all the time, but not under-utilize the system. Deciding where is enough for performance, is a very non-trivial thing.

### Batching

Batching usually means:
- Marshaling multiple operations together
- Send them at once
- Un-marshal an process them in parallel 
- Works well if the system is heavily IO-bounded
- Very good for increasing throughput, not that good for lowering latency

# Prof. Ousterhout's Paper

We had a paper for this session from John Ousterhout.
The paper mentions some adages that are to be kept in mind for any person who does systems measurement. 
The main rules are:
- **Never trust a number generated by a computer:** Benchmarking code is just as likely to be buggy as the implementation code, so treat each measurement with doubt.
- **Always measure one level deeper:** When measuring a high level property (e.g. latency or throughput), it is important to do some micro-benchmarking, especially for latency, since without it, you cannot understand what limits the behavior of your system.
