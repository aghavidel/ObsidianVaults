## Traps

- Traps are the general way that the user code may access the OS.
- Most traps are actually *errors*, like the square root of a negative number, or divide by zero. We use traps here to actually *kill* the program, not to serve it!
- The useful ones however are not, most importantly **system calls** and **page faults**, which signals the OS to fix something or serve someone. 
- Not all traps return things, the error ones in particular may just kill the program and do nothing else.

### System Calls

System Calls (or Syscall as we will refer to them many time) are a special kind of trap that exists to serve application purposes.

Bare in mind the following:
- Executing OS code is hard and complicated, it's best for us to lift that burden off the shoulder of the end user.
- You should not **trust** applications to use the OS correctly, they can be stupid, or even worse, malicious!

Thus, Syscalls are an abstract way for the user program to access the kernel. The trap is served inside the system call and then once we return, we perform the next instruction (and possibly return some return code).

>[!FAQ] Trap vs. Interrupts
>Traps are part of a program, and therefore it is always obvious who did it and why, interrupts on the other hand come whenever the hardware pleases (like IO completion interrupts), and when they do,  they may not have any obvious effect.
>
>Technically, we say that interrupts are *asynchronous* with respect to the CPU (i.e. they run in parallel and are independent). Traps on the other hand are *synchronous* events and this let's us know who did it (so we can probably tell it to do something now).

>[!IMPORTANT] Software Interrupts
>What we called interrupts until now are more precisely, *Hardware Interrupts*. We also have *Software Interrupts*, which are actually generated by the program, but they actually trigger an interrupt as part of the instruction that they should do. 
>
>One important software interrupt in the x86 CPU has the code `0x2e` which is the good old **Trap** instruction that software uses to access the CPU. So in this sense, the general concept of going from the user space into the kernel is what we shall now call software interrupt, but the most widely used *implementation* of this is the Trap that we say.

## Upcalls

Once we are in the kernel space, we can return into the user space by using signals called *Upcalls*. These usually need to be set up by the user code itself (they can use *signal handlers* which we will return to later).

The mechanism is that the OS will use these signals to invoke a code *in the user space*. For example, you can create a timer that once expired, creates an upcall into a user space program (an alarm maybe).

Another important use, is *debuggers*. When a bug happens (say divide by zero), the OS will usually just kill the program, you can however attach a handler to all divide by zero signals in your program, and this means that when the OS detects the divide by zero, it first checks for any handles on that error, and after it sees your handle, it will execute code in the user space (for example, an alarm box coming up saying that you divided by zero in this particular line).

## Processes

As we said, **processes are abstractions of memory**, and we usually think of them in terms of address spaces. In a modern OS, this address space may be shared between processes, but this class uses sixth edition Unix which does not do this.

Also remember that the abstraction of the CPU in different processes is called a *thread*, and one really important thing that we need to define before we'll be able to discuss threads, is **Execution Context**.

We will see this in detail at some point, but execution context is what we need to have on hand to "restore" the execution of a process after we stop doing it. This is a hard thing to do, and we'll have to define the context very carefully for this.

>[!IMPORTANT] Something to Add to Address Space Definition
>In the previous model of the address space, as we said, the `DATA` portion contains the global variables, however, depending on whether the variable is initialized or not, this portion will split into two.
>The initial portion (right after the `CODE` portion) is the initialized variables, but the portion after it is called `BSS` which stands for **Block Started by Symbols**, and this portion will contain the uninitialized variables.
>We also have the term *extended address space*, which is all we use for the process that is actually not in the memory (i.e. not in the conceptual address space), like in the disk or even the screen. To access the extended address space, a process will HAVE to use the OS for help.

### The Heap

Heap refers to last upper portion of the address space, which we called also the dynamic memory. This is the portion where we store variables created with `malloc()`, and we address them like all other variables.

The problem however is that since this part shrinks and expands, we have to keep track of it somehow, and to do this, we use *pointers*.

If you are familiar with C (hopefully), this isn't new to you. All that bears mention here is that:
- We use pointers to point to variables inside the Heap.
- Pointers themselves NEED to be stored either in the global variable section (i.e. data) or in the return value or local variable of some function (so in the stack frame).

To see this in action, take this piece of code:

```c
int nPrimes;                                        // In BSS
int *prime;                                         // Also in BSS
int main(int argc, char *argv[]) {                  // In stack
	int i;                                          // In stack
	int current = 2;                                // In stack
	nPrimes = atoi(argv[1]); 
	primes = (int*) malloc(nPrimes * sizeof(int));  // Whatever this creates, goes to 
													// the Heap
	primes[0] = current;
	for (i = 1; i < nPrimes; i++) {
		int j;                                      // In stack
		NewCandidate:
		current++;
		for (j = 0; primes[j] * primes[j] <= current; j++) {
			if (current % primes[j] == 0) {
				goto NewCandidate;
			}
			primes[i] = current;
		}
	}
	return 0;
}
```
It's important that you get this right NOW!

## The `Syscall` API

With all these abstractions, there comes an interface, or API as we call it. For starters, we need the API that we use to manage processes. These are the Syscalls `exit()`, `fork()` and `exec()`.

### The `fork()` Syscall

When `fork(void)` is called within a process (called the *parent*), it returns an integer called PID, with type `pid_t`, which uniquely identifies a new process (the *child* process) that is an exact copy of the address space of the parent process.

>[!IMPORTANT] A Fun Quirk of `fork`
>Essentially , `fork` returns *twice*!
>1. Once in the parent, with the PID of the new child process.
>2. Another time **in the child**, with the unique return code of 0.
>
>Thus, you can write one code for the parent and one code for the child, but *run them in the same file* by checking what `fork` has returned. If it's 0, you are the child, if it's not zero, you are the parent.
>
>This is essentially how *shells* work (i.e. `bash`, `tcsh`, etc.), if you run say `/bin/ls` in a `bash` shell, then it first forks a new child, and then runs the `/bin/ls` code inside it, and then once it's done, the parent (your terminal!) shows you the result.

At first, the child is *exactly the same* as the parent. The only distinguishing feature between them is the PID, which the kernel holds.

How would you hold this data?

### The PCB

The Process Control Block, or the PCB, is the data structure that most kernels use to maintain data around which processes are active. For the sixth edition Unix, this data structure looks like the following:

- **PID**: The process identifier. An unsigned integer that uniquely identifies the PCB, and the process. You can store them in the `short` type.
- **Return Code:** An 8 bit field, set once the process returns.
- **Link:** A pointer to another PCB. Usually the *sibling* of the process. We'll return to this later …

### The `exit()` Syscall

Kills the process and returns it's integer argument (`exit(int)`). This Syscall actually never returns, it sets the argument into the `return code` field of the PCB and then just stops.

>[!FAQ] Returning From `main()`
>Using `exit()` is the only legitimate way to terminate a process, as it makes sure that the return code gets set to an appropriate value.
>
>However, we usually don't do that! We return a code (usually 0) from the `main()` function. Well it turns out that C actually has a hidden *startup function* that actually **runs `main()`** when you execute your program. 
>
>The code is very simple, just `exit(main())`!


### The `wait()` Syscall

Using `pid_t wait(int*)`, we can wait in the parent process for any child process to return. Once this happens, this Syscall will return the PID of the dead child process, and the return code of that process will be put in the pointer given in the argument.

>[!BUG] Common Bug
>You'll implement this Syscall in the kernel assignments. When you do, do not forget to **free the PCB of the dead child process!**.

If more than one child return, one would be chosen at random to return. If there are no dead child process, the parent will be **blocked**. In other words, if no child process ever dies, the parent will be forever stuck. It's your job to make sure this does not happen!

It is also possible that the call returns instantly if there are already some dead child processes!

>[!IMPORTANT] Fork And Wait
>Check this code:
>```c
>short pid;
>if ((pid = fork()) == 0) {
>	// Put code here for the child process
>	exit(n);
>}
>else {
>	int returnCode;
>	while (pid != wait(&returnCode));
>	// Here, handle the case where a child with 'returnCode' terminates!
>}
>```
>This is exactly what the shell uses to run your commands!
>You'll be using this segment a lot ...

#### Keeping Track of Processes

For PIDs, we may only use 16 bits in the sixth edition Unix, so you should not create and reuse these PIDs too quickly. If you do, it's possible to make the unique mapping between processes and PIDs *ambiguous*.

Some fine details need to be addressed here for this, for example:

>Once `exit` is called, you should not free the PCB *right away*, you can free the address space, but it's not instantly obvious that the parent has received the return code of the recently terminated process. You free the PCB, only when the parent is alive and running again.
>Same goes for the PID itself, unless the parent was already in `wait` for it.

So how would we do that?

The common solution is to designate recently terminated processes as **Zombie Processes**. We treat zombies like the following:

- The PCB may only be freed up after the parent has successfully executed `wait` on that PID. This is the clean way of destroying zombies.
- If the parent calls `exit` before calling `wait` enough time to "reap all the zombies", then we'll be in trouble. In the sixth edition Unix, and most other operating systems, a special PID of 1 is the *reaper process*, whose sole purpose is destroying zombies.
  To do this, once a child loses it's parent, exits, and becomes a zombie, the OS will **reparent** it to the reaper, and once this is done, the reaper will repeatedly execute `wait` until all the zombies are gone.
  This is computationally heavy, but necessary to keep memory corruption bugs away.
  
  Since engineers are bad with names, they preferred to call the reaper, the `Init` process for whatever reason, which is like calling "King Geldof, Destroyer of Worlds" Gary.

### The `exec()` Syscall

There are many forms of this System Call, but in it's base form, this is the way that a recently forked address space, is turned into a new process.

We focus on the specific Syscall named `execl()`, which is the one that we'll be using in this class. What this does, is that it wipes the entire address space of it's calling process, and it replaces it with the new executable that we give it. This transforms the current process into "something else".

To see how this is done, picture the prime finder program that we discuss above, let's say we put it in `/home/argh/bin/primes` (this is the full executable). To run it in the forked process we can do:

```c
int pid;
if ((pid = fork()) == 0) {
	// Somethings we'll have to do here, let's forget that for now ...
	execl("/home/argh/bin/primes", "primes", "300", 0);
	/* Read the man page, but int brief, execl accepts variable number
	 * of arguments, but the 0 in the end is needed to symbolize the NULL
	 * pointer that we need to tell the function that we are finished.
	 * The first argument is the path to your executable.
	 * The second argument is the name of the new process.
	 * The rest will be passed as arguments to the executable itself.
	**/
	exit(1);
}
// The parent continues from here ...
```

You might ask what's with that `exit(1)` up there? 
Well, as always, you should never expect Syscalls or `malloc` to actually work. So what if the path given is not correct? We'll end up going all the way down and executing code that was meant for the parent, *in the child*!

The exit Syscall up there is a safeguard, if `execl` pulls through, the address space gets wiped and thus that Syscall *will never be executed*, if things go south though, we reach this Syscall and immediately terminate before we do something stupid. 

Code can be written here to inform the parent about what exactly happened using the returned exit code, but we are not supposed to do anything other than that, the application needs to handle this now.
