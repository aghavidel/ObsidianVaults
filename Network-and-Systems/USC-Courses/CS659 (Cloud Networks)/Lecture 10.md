## NIB

The NIB here is very similar to the eventually consistent database that we introduced when discussing Onix.

It is important to note that:
- NIB is maintained **in-memory**, it keeps all of the network entities in separate tables
- NIB is NOT durable. 
- It is a pub-sub system that can batch multiple writes and submit them atomically
- Since it is a pub-sub system, it allows for the implementation of triggers. This means that you can choose to wait on any change to a field in any entity of choice.
- The intent, sub-intents and flow records generated by them will also be held in the NIB.

The notification API is causally consistent (or sequentially consistent as the paper says), if an app is waiting on two events (A or B) and A happens before B, then we receive the notification of A first and then get B.

## Core Services
### Config Manager
It provides the interface for reading/writing the controller *application* configurations. The configuration are validated by separate applications and a 2PC (of which one way to implement it would be with shadowing, see the lectures for the Advanced OS class) is used to atomically commit them once verified.

### Topology Manager
Maintains consistent view into the topology state and keeps it in the NIB. If any change in the topology occurs, then it will commit that change to the NIB. It will also collect flow statistics from switches.

### Flow Manager
Computes flow entries from sub-intents for each switch and then forwards them for installation. It will also schedule reconciliation requests when needed.

### OpenFlow Frontend
The main interface to the actual switch instances, it will pass any flow request to the switches and ACK their installation.

It will also serve Packet-In flows for collecting packets of interest for applications. Each application can register a packet filter for packets that it wishes to collect and OFE will install the flow instruction required for it.
Similarly, Packet-Outs can also be served from the OFE to tell a switch to send a packet from a desired interface when an application requests it.

## Routing Engine (RE)

Before really discussing this, let's setup an example.
First, remember that switches can be aggregation blocks (i.e. switches made up from smaller switches).

![[Pasted image 20240212163508.png]]

We receive a path prefix from a neighbor, saying that we have a path to a prefix `1.2.3.0/24` from a neighbor. We usually would update the FIB and then re-advertise this.
To be notified of this in an SDN domain, a **routing application** in Orion will setup filter for BGP update messages carrying prefix advertisements. 
When this configuration is placed, then when this advertisement comes in, it is encapsulated as a Packet-In and then sent to the controller. This Packet-In will then be consumed by the application and a message is published to the NIB.

![[Pasted image 20240212164011.png]]

The Routing Engine (RE) is the consumer of this NIB update. It will create a flow for this advertisement (here an output action from a port group) and write that to the NIB.

The consumer of this event would be the Flow Manager, and upon consuming this message, it will install that flow to the destination switch as required. 

So the hierarchy is like this:
- A Routing Application would distribute a routing instruction by reading the topology
- The Routing Engine would:
	- Compute a path based on the collected route
	- Sequence the installation of this path on the topology
- The Flow Manager would install these path instructions and return the ACK

>[!NOTE] The Importance of Sequencing
>Doing things in the right order matters. If done wrong, we can have packet drops.
>Here is an example:
>
>![[Pasted image 20240212170236.png|300]]
>
>Here, we want to re-route from $S_2$ to $S_3$. To do this, we should:
>1. Install the flow on $S_3$
>2. Change the flow on $S_1$ to switch direction
>3. Cleanup the flow on $S_2$
> 
>Not honoring this order would cause packet drops.
>Note that only SDN can do this, since it has a global view into the network!

## Other Applications

Any other application that wants to interface to the controller, would make use of a common library. These include:
- Common functions for all apps
- Interfaces to the NIB and health monitoring

It will also provide necessary code for implementing life-cycle management, where it will run multiple instances of an application and then elect one as leader. This allows quick failover in the event of some problem in an application instance.

Thus, Orion becomes resilient to internal component failure. 
It is a different story for NIB though ...

## NIB Failover

Remember that NIB is NOT durable, so we are not worried about losing state.

When NIB fails:
- Orion creates a new NIB instance
- Reconciles switch state with intent by looking into the switches and comparing  them with what is collected from the Config Manager
- Reprogram switches if some discrepancy is detected in the previous step

Reconciliation of course has many dependencies, so we need to wait until all the intent is built up again before finishing reconciliation.

It is important to note that the intent by which we actually generate the desired state of the network should persist across **ALL** failures. Thus, it should be kept somewhere (like a disk). Most likely candidate for this would be the management plane.

The whole failover process of the controller follows like this:

![[Pasted image 20240212171822.png|400]]

1. The Config Manager reads the static intent from the Management Plane
2. The intent is reported to the Topology and Flow manager, this triggers the reconciliation with the current network state, where we get the actual topology state and the set of flows currently installed on the switches
3. This data is then distributed among all application and the Routing Engine and they will compute the set of flows that still need to be pushed
4. The set of calculated flows are given to the Flow Manager and once it is pushed to the switches, we are practically back to the stable state

## Deployment Considerations

### In-Band vs Out-of-Band Control Plane

We have already discussed this, but:
- An In-Band control plane will run on the data plane
	- Could reduce costs
	- It is weird, since the controller should setup routing for itself first while the switches have no idea how to contact the controller first!! There is a circular dependency to it.
- Out-of-Band Control Plane will have its own network:
	- The networking will be done with traditional protocols (e.g. OSPF)
	- It won't have to be a behemoth of a network, since not much capacity is needed

Orion actually uses a hybrid of both. It is not detailed exactly why did it.

### BGP Integration

Google has 2 WANs, 
- There is B4, used for their own data centers (which we will visit soon!)
- And then B2, which faces the public

To glue these two networks together, BGP is needed. Integrating it into the controller will make all of it look like a single network to the controller, so they had to do it.

### (OLD) Jupiter Decomposition

>[!WARNING]
>The Jupiter here is the OLD Jupiter, without the OCSs.

When OCSs were not yet introduced into Jupiter, Google did some really fancy things:
- All aggregations blocks will have their *own* Orion instance as a controller
- Each spine block in a failure domain will have an Orion controller for itself as well

This adds new complexity, since an aggregation block Orion instance needs to interact with the instance in the spine. For this, the Inter-Block Routing Controller (IBR-C) is used. 
It will see the spine and aggregation blocks as a *single node* each and it sees a bunch of links between them. This is referred to as a *virtual topology*, and that is quite apt here since from the perspective of the IBR-C, each node is really just a single entity, whereas the node itself is a spine or aggregation block. Thus, the IBR-C will **NOT** control the switches directly, and will subscribe to the spine/aggregation block NIBs.
It will then program them as needed.

The reason that Google is using this many individual controllers, is because they are staunchly committed to making sure that a single controller never spans multiple power domains. Note that aggregation blocks are not 4-colored, since they are a particularly small unit compared to the spines and the OCSs later.

![[Pasted image 20240212175009.png]]

It goes without saying that an IBR-C failure would really bring down a big chunk of the network. This is really the big price that Google is paying, compared to what Facebook did. While Facebooks system would most likely not be able to react as fast to failures, Google had to be very aggressive with using SDN controller to uphold its rules.
